# Масштабирование и отказоустойчивость
* Будет производиться горизонтальное масштабирование, т.к. вполне себе можно уводить обработку запросов и сами запросы в параллелльный контекст. 
* Дополнительно будет использоваться Rate-limiter с ответной мерой приритезациии запросов. В качестве ID можно указывать как-то сами страховые компании и смотреть на строго на кол-во запросов по их ID.

* Зоны деплоя: Москва, Екатеринбург и Новосибирск. Все 3 изолированные и этот вариант будет изображён на схеме. Зоны смещены ближе к левой части РФ, в основном, из-за плотности населения и на случай, если мск сервер упадёт.
    * Возможен немного иной вариант, но я не увидел в нём преимуществ... Зоны деплоя: Москва, Новосибирск, Якутск.
        * Я так почитал: ничего не мешает сделать изолированный кластер в Москве и один геораспределённый на Новосибирск и Якутск. Буду придерживаться подобного способа, в ином случае сделать у изолированных кластера.
        * Выбрал так -> потому что машины довольно много, запросов на их страховки, очевидно, тоже много.. помимо этого в мск огромная плотность населения, такой сервер, как минимум, обязательно надо изолировать от остальной часит РФ.

* Для гео-балансировки нагрузки будет использоваться GSLB.
* В качестве фейловер-стратегии будет использоваться Active-active подход, т.к. предъявлены высокие требования доступности к системе.
* Для БД будет использоваться Patroni.
